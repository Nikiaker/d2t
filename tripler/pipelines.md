# app_text_pipeline.py
## Text-First Extraction with Normalization
### The simplest text-first two-batch pipeline, plus optional normalization.
Step 1 (batch): JSON → references via TEXT_GENERATION_SYSTEM_PROMPT (with enable_thinking:false). Step 2 (batch): references → triples via TRIPLES_FROM_TEXT_SYSTEM_PROMPT, a plain text-to-triples extraction with no catalog/inventory/rules. Two parallel batches, no sequential per-instance calls. Optional normalize subcommand reuses the same Union-Find predicate normalization as method #1. Clean separation: JSON → text → triples → (normalize).

# app_rules_text_pipeline.py
## Rules-Iterative Refinement
### Rules-driven pipeline with iterative rule refinement
Step 1: LLM generates initial domain rules {predicates, example_triples, example_text, guidelines} (RULE_CREATION_SYSTEM_PROMPT). Step 2 (batch): JSON → references (same text-generation batch). Step 3 (iterative loop, up to --max-rules-revision-rounds): for each instance text, the LLM checks rule feasibility (RULE_FEASIBILITY_SYSTEM_PROMPT → possible/reason/rule_gaps); on the first failing text, the rules are revised (RULE_REVISION_SYSTEM_PROMPT, keeping good rules, adding to cover the gap) and instance checking restarts; stops when all texts pass or the round cap is hit. Step 4 (batch): all texts → triples in one batch using the final rules (TRIPLES_FROM_TEXT_WITH_RULES_SYSTEM_PROMPT), preferring rule predicates and mimicking example-triple formatting. Output includes initial/final rules and revision history.

# app_text_predicate_catalog_stable.py
## Evolving Catalog
### Text-first pipeline that also builds an evolving predicate catalog with a stable-window heuristic
Step 1 (batch): all instances → natural-language references via TEXT_GENERATION_SYSTEM_PROMPT. Step 2 (sequential): instance 0 triples are free-extracted from its text; every later instance's triples are extracted with CATALOG_GUIDED_TRIPLES_SYSTEM_PROMPT, receiving the current predicate catalog (name + one example triple per predicate). The model reuses catalog predicates or invents a new one only when necessary; new predicates are added to the catalog with an example triple, so it evolves instance-by-instance. Fully sequential in the triple step (no batch). No normalization step. Same as #3 for text generation (batch) and the initial sequential catalog-building triple extraction. A stability counter tracks consecutive instances that introduce no new predicate; when it reaches --stable-window (default 20), the catalog is frozen and the loop breaks. All remaining instances are then extracted in a single OpenAI Batch with the frozen catalog (extract_catalog_guided_triples_batch); predicates discovered in this batch are intentionally NOT added back to the catalog. Output records whether/where stability was reached and the sequential-vs-batched split.


4. Method 4 — Text-First Catalog-Guided Extraction with Stable-Window Batch Handoff
Implementation: tripler/app_text_predicate_catalog_stable.py
Method 4 is a hybrid text-first data-to-triples pipeline that combines an evolving predicate catalog with a stability-triggered transition from sequential to batch processing. It is designed to keep the predicate vocabulary consistent across instances while reducing the latency overhead of per-instance, order-dependent LLM calls.
The method comprises three logical stages.
4.1 Stage 1 — Reference text generation (batched)
Let $D = \{d_1, \dots, d_N\}$ denote the set of $N$ raw structured instances obtained from the input JSON after instance extraction (the shared extract_instances routine supports top-level keys forecasts, list, an explicit --top-level-key, or a bare list). In the first stage the model is invoked once per instance under a text-generation system prompt, $P_{\text{txt}}$, whose objective is to convert one structured data instance into concise natural language and to return the result as a JSON object of schema {"text": "..."}. The prompt further instructs the model to capture the most important information, trends, extremes, and notable conditions, and to summarize time series (e.g., weather forecasts) at a high level rather than listing every data point.
All $N$ requests are packaged as a single OpenAI Batch API job (JSONL input, each line one request with a stable custom_id of the form instance-<id>). The batch is submitted, polled until termination, and its output JSONL is parsed back into a mapping $\tau : i \mapsto t_i$, where $t_i$ is the generated reference text (the reference) for instance $d_i$. This batched stage yields, for every instance, a natural-language reference $t_i$ that constitutes the intermediate representation from which triples are subsequently derived.
4.2 Stage 2 — Sequential catalog-driven triple extraction
The second stage maintains a mutable predicate catalog $C$, initialized as empty. The catalog is a set of entries $\{(\pi, e_\pi)\}$, where each entry associates a predicate label $\pi$ with an example triple $e_\pi = (s, \pi, o)$ in which that predicate was first observed. The catalog thus carries both a normalized vocabulary and a small set of usage examples that serve as in-context guidance for the extraction model.
The instances are processed strictly in order:
1. Bootstrap instance (i = 0). Because $C$ is empty, the reference $t_0$ is sent to the model under a first-instance system prompt, $P_{\text{first}}$, that simply asks for semantic triples from the text with concise lower_snake_case predicates and no duplicates. This yields a set of triples $T_0$.
2. Catalog-guided instances (i ≥ 1). For each subsequent instance $d_i$, the reference $t_i$ is sent under a catalog-guided system prompt, $P_{\text{cat}}$, in which the current catalog $C$ is serialized and injected into the user prompt. The model is instructed to use only predicates from the provided catalog when possible and to introduce a new predicate only when none of the catalog predicates can describe the fact. This yields triples $T_i$.
After each instance, every triple in $T_i$ is inspected. If a triple contains a predicate $\pi \notin C$, a new entry $(\pi, e_\pi)$ is added to $C$, where $e_\pi$ is set to that triple (the witness of first occurrence). A flag added_new_predicate records whether at least one new predicate was introduced during the processing of $d_i$.
4.3 Stage 3 — Stable-window heuristic and batched tail processing
The novelty of Method 4 lies in the stopping criterion that bridges Stage 2 and a fully batched final phase. A counter stable_count tracks the number of consecutive instances that did not introduce any new predicate; it is reset to zero whenever a new predicate is added. Let $W$ denote the stable window parameter (configurable via --stable-window, default $W = 20$). The sequential phase terminates as soon as stable_count $\geq W$ and at least one instance remains unprocessed. Let $i^\star$ be the index at which this condition is first met; the catalog $C$ at that point is declared frozen.
All instances $d_{i^\star+1}, \dots, d_N$ (the tail) are then processed in a single second OpenAI Batch, again under $P_{\text{cat}}$ and with the frozen catalog $C$ injected into every request. Two design choices are important here:
- The tail is parallelized, hence the cost of the remaining $N - i^\star - 1$ LLM calls is amortized into one batch.
- Predicates that first appear within the tail are not added back to $C$. The catalog is finalized at the moment of stability, which guarantees that the predicate vocabulary presented to a human evaluator is fully determined by the sequential phase and does not silently grow during batch processing.
4.4 Output and provenance
The method returns a JSON document containing, for each instance, the generated reference $t_i$ and the extracted triples $T_i$, together with the flattened all_triples list, the list of unique_predicates, the frozen predicate_catalog, and a predicate_discoveries log recording, for each predicate, the instance id and witness triple at which it was first introduced. The output additionally records stable_reached (boolean), stable_reached_at_instance_id, sequential_instances_processed, and batched_instances_processed, so that the split between sequential and batched computation is fully auditable.
In summary, this method explicitly trades off two competing objectives: (i) a self-consistent, human-interpretable predicate vocabulary that is built incrementally from concrete examples; and (ii) the throughput benefits of batched inference, which are recovered adaptively once the vocabulary has converged. The window parameter $W$ controls this trade-off: smaller values trigger earlier batching at the risk of an incomplete vocabulary; larger values defer batching and increase the per-instance LLM cost of the sequential phase.
5. Method 5 — Two-Stage Text-First Batch Extraction
Implementation: tripler/app_text_pipeline.py
Method 5 is the structurally simplest of the three selected approaches. It decomposes the data-to-triples problem into two independent, fully batched LLM stages, with an optional third normalization stage reused from the baseline pipeline. The method deliberately avoids any inter-instance coupling during extraction: each reference and each triple set is produced independently and in parallel, which makes the method stateless and easy to reason about, at the cost of not enforcing predicate consistency during extraction.
5.1 Stage 1 — Reference text generation (batched)
As in Method 4, an OpenAI Batch is assembled in which every instance $d_i$ is paired with the text-generation system prompt $P_{\text{txt}}$, whose purpose is to produce a concise natural-language summary that captures the most important information, trends, extremes, and notable conditions, and summarizes time series at a high level. The only technical difference from Method 4 is that the request body carries an additional chat_template_kwargs : { enable_thinking : false } directive, intended for models that expose a reasoning toggle; this suppresses chain-of-thought tokens in the output and keeps the generated reference strictly to the summary text. The batch output is parsed into the mapping $\tau : i \mapsto t_i$ of references.
5.2 Stage 2 — Triples-from-text extraction (batched)
A second OpenAI Batch is then assembled in which every reference $t_i$ is paired with a triples-from-text system prompt, $P_{\text{tr}}$, whose objective is to extract semantic triples from natural language text, returning JSON of schema {"triples":[{"subject":"...","predicate":"...","object":"..."}]}. The prompt imposes two light constraints: it instructs the model to preserve the full meaning of the input text and to keep predicates in lower_snake_case when possible, and to avoid duplicate triples. Crucially, no predicate catalog, no domain rules, and no per-instance constraints are passed to the model. Each instance is therefore an independent text-to-triples problem, and the batch can be fully parallelized.
The batch output is parsed back into a mapping $i \mapsto T_i$ through the same JSONL-parsing routine used elsewhere in the codebase, and a flattened all_triples list, per-instance triples, and unique_predicates are assembled.
5.3 Stage 3 — Optional post-hoc predicate normalization
Because Stage 2 imposes no inter-instance vocabulary control, Method 5 optionally invokes the same predicate-normalization routine defined in the baseline module and described in Method 1. Normalization is executed as a separate normalize subcommand that reads the output of the extract step. The routine operates on the flattened list of triples and iteratively merges semantically equivalent predicates:
1. Let $\Pi$ be the set of distinct predicates present in the extracted triples.
2. A Union-Find structure over $\Pi$ is initialized with every predicate in its own singleton class.
3. For each round $r = 1, 2, \dots$ (bounded by $2|\Pi|$):
- The model is prompted with the current set of canonical predicates (class representatives) and asked to propose candidate equivalent pairs under a candidate-pairs system prompt.
- If no candidate pairs are returned, or if the candidate set repeats a previously seen round signature, the loop terminates.
- Otherwise, every candidate pair is sent to the model under a strict equivalence system prompt that returns {equivalent, confidence, reason} and is instructed to judge equivalence strictly (mergeable in a knowledge graph), not mere relatedness.
- Pairs judged equivalent are merged in the Union-Find structure. If a round produces no merges, the loop terminates.
4. After termination, each predicate is mapped to the canonical representative of its class, defined as the first member of the class (deterministic, order-based choice). The triples are then rewritten with these canonical predicates.
The normalization output records the predicate classes, the full pairwise comparison log, and the counts of comparisons performed.
5.4 Output and design trade-off
When the normalize step is used, the final output combines (i) generated references, (ii) extracted triples, and (iii) normalized triples alongside the canonical mapping and the comparison audit trail. When it is omitted, the method produces references and raw triples only.
Method 5 can thus be summarized as a clean two-batch reference-then-triples pipeline, with an optional third batch-driven normalization stage. Its main appeal is simplicity and determinism of the execution pattern: the number of LLM jobs and the lack of state during extraction make the method easy to reproduce and reason about. Its main limitation is that predicate consistency is not enforced at extraction time; it is instead retrofitted, if desired, by the Union-Find normalization step, which itself incurs additional LLM calls and depends on the model's pairwise equivalence judgments.
6. Method 6 — Rule-Iterative Refinement Text-to-Triples
Implementation: tripler/app_rules_text_pipeline.py
Method 6 introduces an explicit notion of extraction rules that act as an intermediate, human-inspectable artifact between the domain declaration and the final triple extraction. Instead of building a predicate vocabulary bottom-up from observed triples (as in Methods 3 and 4), the rules are generated top-down from the domain name, then iteratively validated and revised against the generated references until they admit triple extraction for every instance. Only then is a single batched triple-extraction run executed under the finalized rules.
6.1 Stage 1 — Initial rule generation
Given the user-supplied problem domain string $\delta$ (e.g., weather forecast), the model is invoked once under a rule-creation system prompt, $P_{\text{rules}}$, and asked to design extraction rules for a domain. Its response is constrained by a strict JSON schema to contain exactly four fields:
$$R = \Big( \Pi_R,\ E,\ \text{exampleText},\ G \Big),$$
where $\Pi_R$ is a list of predicate labels, $E$ is a list of example triples $\{(\sigma_k, \pi_k, \omega_k)\}$ using those predicates, $\text{exampleText}$ is a short natural-language passage consistent with the example triples, and $G$ is a list of free-text transformation guidelines. The response is sanitized by _normalize_rules, which deduplicates predicates and guidelines, discards malformed example triples, and falls back to previous values for any empty field.
The resulting $R_0$ constitutes the initial ruleset. Conceptually, $R_0$ is a self-contained specification of how the model believes instances of the domain should be verbalized and triplelized, complete with concrete formatting conventions embedded in the example triples.
6.2 Stage 2 — Reference text generation (batched)
The reference-generation batch is identical to that of Methods 4 and 5: every instance $d_i$ is sent to the text-generation system prompt $P_{\text{txt}}$ within a single OpenAI Batch, producing references $\tau : i \mapsto t_i$.
6.3 Stage 3 — Rule validation and iterative revision
The core of the method is an iterative loop, bounded by $R_{\max}$ (parameter --max-rules-revision-rounds, default $20$). The loop maintains a current ruleset $R$, initialized to $R_0$, and operates as follows for each round $r = 1, \dots, R_{\max}$:
1. Feasibility scan. The loop iterates over instances in order. For each reference $t_i$, the model is invoked under a rule-feasibility system prompt, $P_{\text{feas}}$, which receives the current rules $R$ serialized as JSON and the text $t_i$, and returns {possible, reason, rule_gaps}, where rule_gaps is a list of textual descriptions of what is missing from $R$ in order to extract triples from $t_i$.
2. Pass condition. If the scan reaches the last instance without encountering a possible = false judgment, the rules are declared validated against all texts (rules_validated_all_texts = true) and the loop terminates. A record of the round, including the number of instances checked and the failing instance id (if any), is appended to rules_validation_rounds.
3. Failure and revision. As soon as a reference $t_{i^*}$ is judged infeasible under $R$, the scan halts (this is a fail-fast strategy). The revision system prompt, $P_{\text{rev}}$, is then invoked with the domain $\delta$, the current rules $R$, the failing text $t_{i^*}$, the failure reason, and the enumerated rule_gaps. Its response is again constrained to the four-field rules schema. The model is instructed to keep existing high-quality rules, but add or adjust what is necessary to cover the failing case. The sanitized result replaces $R$ as the new current ruleset, and a revision record (round, failed instance id, reason, gaps) is appended to rules_revision_history.
4. Restart. Because revising the rules may break previously validated instances or expose new gaps, the scan is restarted from instance $d_1$ in the next round. The loop thus monotonically accumulates coverage, but backtracks the scan position whenever the rules are modified.
If the budget $R_{\max}$ is exhausted before all texts are validated, the method emits a warning and proceeds to final extraction with the best-effort ruleset; the output records that validation was incomplete.
This stage implements a generate-test-revise loop in which the rules are the artifact being refined, the reference texts act as test cases, and the feasibility prompt acts as a model-internal test oracle. It is analogous in spirit to iterative prompt optimization, except that the optimized object is a structured set of domain rules rather than a free-form prompt.
6.4 Stage 4 — Final batched extraction under finalized rules
Once the validation loop has terminated, a single OpenAI Batch is submitted in which every reference $t_i$ is paired with a triples-from-text-with-rules system prompt, $P_{\text{tr}\&R}$. This prompt instructs the model to extract semantic triples from the natural language text using the provided rules, to follow the rule guidelines, and to mimic the formatting style of the example triples, and to prefer predicates from the rule predicate list whenever possible. The rules $R$ are serialized and injected in each request. The batch output is parsed into $T_i$ and aggregated into all_triples and unique_predicates.
Two design consequences follow from this design. First, the predicate vocabulary of the output is upper-bounded by $\Pi_R \cup \{\text{predicates invented during batch extraction}\}$, but in practice it is heavily biased toward $\Pi_R$ because the model is told to prefer it. Second, because rules are finalized before the batch is submitted, all triple extractions are performed against the same ruleset, which makes the extracted triples easier to compare across instances and the ruleset itself a standalone deliverable that a human expert can inspect and edit independently of any triple.
6.5 Output and provenance
The method produces a JSON document that contains, in addition to the per-instance references and triples and the usual flattened aggregates, the full lineage of the rules: rules_initial, rules_final, rules_validated_all_texts, rules_validation_rounds (per-round check counts and failing instance), and rules_revision_history (per-revision failed instance, reason, and gap list). The method therefore yields a transparent audit trail of how the extraction specification was generated and refined, which is a distinctive property compared with the catalog-based methods, whose implicit specification is revealed only post hoc through the discovered examples.
In summary, Method 6 treats the triples-extraction problem as a specification-authoring problem: the model authors a candidate ruleset, tests it on the generated references, revises it until it is sufficient, and only then performs a single batched extraction. This shifts the cost of inter-instance consistency from post-hoc normalization (Method 5) or in-context catalog growth (Methods 3 and 4) to an explicit, iterative, auditable specification step.
