\section{Meaning representation}

\subsection{Data Collection}

The experimental evaluation in this work requires structured data from diverse domains. To obtain such data, \emph{quintd}~\cite{kasner2024beyond} is used, a framework for collecting \emph{ad hoc} data-to-text datasets. Quintd downloads up-to-date structured data from real-world APIs. The framework supports five domains: weather forecasts, mobile phone specifications, ice hockey game summaries, health statistics, and world knowledge entities.

From the five domains available in quintd, four datasets are used in the experiments:

\begin{description}
  \item[\textbf{GSMArena}] Mobile phone specifications scraped from the GSMArena website. Each instance describes a single phone model with nested categories (Network, Launch, Body, Display, Platform, Memory, Camera, Battery, etc.) containing attribute--value pairs.
  
  \item[\textbf{OpenWeather}] Five-day weather forecasts obtained from the OpenWeather API. Each instance contains a time series of 40 three-hour intervals, with each interval recording temperature, humidity, wind speed, cloud coverage, and weather conditions.
  
  \item[\textbf{OWID (Our World in Data)}] Country-level time series metrics from the Our World in Data project. Each instance represents a single metric (e.g., life expectancy, vaccination rates, reproduction rate) for a specific country, containing yearly data points spanning several decades.
  
  \item[\textbf{Wikidata}] Knowledge graph entities and their properties from Wikidata. Each instance describes an entity (e.g., a country, film, or organization) with a list of property--value pairs (e.g., capital, cast member, language used).
\end{description}

The fifth domain, \emph{ice hockey}, is available in quintd but is excluded from our experiments due to API rate limits and associated costs.

All datasets are provided as JSON files containing arrays of structured records. A \emph{raw structured instance} is defined as a single JSON object representing one self-contained data record from any of these domains. Each instance contains nested fields with structured data---time series, categorical values, numerical measurements, or hierarchical attribute lists---that must be converted into semantic triples. Let $D = \{d_1, \dots, d_N\}$ denote the set of $N$ such instances extracted from the input JSON for a given domain.

\paragraph{Large language model.}
All LLM invocations across the three methods use \emph{Gemma~4 31B IT}~\cite{team2024gemma,team2026gemma}, a 31-billion-parameter instruction-tuned language model released by Google. Gemma~4 uses a hybrid attention architecture: most layers employ sliding-window attention with head dimension 256, while a subset of layers use global attention with head dimension 512. The model is served via \emph{vLLM}~\cite{kwon2023vllm}, a high-throughput inference engine that uses \emph{PagedAttention} to efficiently manage KV-cache memory, enabling batched inference with dynamic sequence lengths.

\subsection{Training Configuration}

The base model for all fine-tuning experiments is \emph{Gemma~4 31B IT} (described in Section~\ref{sec:data-conversion}).

All training is performed on NVIDIA A100-SXM4 GPUs with 40~GB of VRAM, using the PLGrid Athena cluster. Table~\ref{tab:qlora-config} summarizes the complete training configuration.

\begin{table}[h]
\centering
\caption{QLoRA training configuration}
\label{tab:qlora-config}
\begin{tabular}{ll}
\hline
\textbf{Component} & \textbf{Value} \\
\hline
Base model & Gemma 4 31B IT \\
LoRA rank ($r$) & 16 \\
LoRA scaling ($\alpha$) & 32 \\
LoRA dropout & 0.05 \\
Target modules & 420 (all attention and MLP projections) \\
Trainable parameters & ~25M (<0.1\% of base model) \\
Quantization & 4-bit NF4 with double quantization \\
Compute precision & bfloat16 \\
Optimizer & Paged AdamW 8-bit \\
Learning rate & $10^{-4}$ (cosine schedule) \\
Warmup ratio & 0.03 \\
Epochs & 3 \\
Effective batch size & 16 (per-device: 1, accumulation: 16) \\
Max sequence length & 4096--8192 (domain-dependent) \\
Loss type & Completion-only (prompt masked) \\
\hline
\end{tabular}
\end{table}

The LoRA configuration targets all attention and MLP projection matrices in the language model backbone (\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj}, \texttt{o\_proj}, \texttt{gate\_proj}, \texttt{up\_proj}, \texttt{down\_proj}), using a regular expression that scopes the adapter placement to the language model sub-network and excludes the vision and audio towers present in the multimodal Gemma~4 checkpoint. This yields approximately 420 target modules and roughly 25 million trainable parameters---less than 0.1\% of the base model.

The maximum sequence length is adjusted per domain to accommodate the varying sizes of the raw structured instances while staying within the GPU memory budget. Wikidata instances are small (at most a few hundred bytes), so a maximum length of 8192 tokens is used. GSM Arena and OWID instances are larger, and a maximum length of 4096 tokens covers the majority of examples. OpenWeather forecast instances are the largest (approximately 18~KB each), and a maximum length of 6144 tokens is used to retain the bulk of each example while remaining within the activation memory ceiling. Instances exceeding the maximum length are truncated.

After training, the LoRA adapter weights are combined with the frozen base model weights to produce a single, standalone model. This process, known as \emph{weight merging}, computes $W_{\mathrm{final}} = W_0 + \Delta W$ for each adapted layer, effectively absorbing the adapter's learned modifications into the base model. The resulting model contains no separate adapter components and can be served as a standard \texttt{bfloat16} checkpoint. The merged model is a drop-in replacement for the base model: it can be served by the same vLLM inference engine used by the tripler pipeline, with no adapter-loading overhead at inference time. The result is a domain-specialized model that, given a raw structured instance, produces both a natural-language verbalization and the corresponding set of semantic triples in a single decode pass.

\section{Surface realization}

\subsection{Illustrative evolution trace}

The completed Building run in the
\texttt{5\_1krand30m4p1themis/Building\_output/} directory
shows the complete data flow. It was configured for 1,000 evolutionary
iterations, used four worker processes, one island, a population limit of 50,
an archive of 10, one inspiration per prompt, and enabled Themis judging and
JSON evolution tracing. The output contains 948 ordinary program records, 15
records in \texttt{broken\_programs/}, and 896 trace entries. The counts differ
because several iterations produced malformed or duplicate candidates and
because persistent program files document historical candidates rather than
only the final active population.

The initial program was evaluated at iteration zero with a recorded
\texttt{combined\_score} of approximately 0.0300 and a BLEU diagnostic of
approximately 0.1871. The first accepted mutation replaced the one-line
fallback with a predicate map, an empty-input guard, subject grouping, and
multi-triple joining. Its recorded combined score increased to approximately
0.0358, while its BLEU diagnostic increased to approximately 0.4295. Later
mutations introduced linked-subject traversal and relative-clause selection.
The best recorded candidate was found at iteration 794, generation 10, after a
mutation that simplified subject processing and removed quote and angle-bracket
delimiters from object values. It had a recorded combined score of
approximately 0.0676. These values illustrate the mechanics of the evolution
trace and are not held-out test results; the latter are produced separately by
\texttt{final\_test.py}.

The online evaluator uses WebNLG training and development entries to provide
fitness during evolution. The final-test script instead loads the held-out
WebNLG test file and computes BLEU, METEOR, SENLEN, BLEURT, judge scores,
grammaticality, omission, and addition measures. Keeping these two paths
separate makes it possible to use the evolutionary score to drive search while
reporting generalization in the experiments chapter.
